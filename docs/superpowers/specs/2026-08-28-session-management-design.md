# Session Management Design

## Goal

Turn Moh's existing durable session foundation into a complete interactive
session-management experience. Users can resume saved chats, switch among
sessions without cancelling work left behind, browse sessions in the active
project or globally, rename them, and permanently remove them.

An empty chat is not a session. Moh creates durable state only when the user
submits its first message.

## Context

Moh already has one per-user backend, a SQLite session store, lazy per-session
actors, typed Cap'n Proto RPC, and a fullscreen Ratatui client. The backend can
create, open, and list durable sessions. Dropping a terminal client does not
cancel that session's active model run or background jobs.

The current product model still has several limitations:

- plain `moh` eagerly opens or creates a durable default session;
- `moh --new [NAME]` creates a durable session before any conversation exists;
- the TUI is permanently bound to the one session capability passed at startup;
- session listing is CLI-only and scoped to the invocation directory;
- titles are optional immutable names rather than editable display metadata;
- sessions cannot be deleted;
- only successful model history is durable, so failed, cancelled, and
  interrupted visible turns disappear after a backend restart;
- dropping one session capability on a still-open backend connection does not
  explicitly remove that attachment.

This design extends the existing backend, actor, snapshot, and Ratatui
boundaries. It does not replace them.

## Product Decisions

- The client owns at most one durable session attachment.
- Switching detaches the previous session without cancelling its work.
- `/new` takes no arguments and always opens a fresh ephemeral chat.
- Plain startup and current-session deletion resume the most recently active
  running session in the active project, or show an ephemeral empty chat when
  none is running.
- A session is running when it has an active model request or at least one
  running background job.
- Empty chats have no durable ID and do not appear in listings.
- The first submitted message materializes the session before its model run is
  dispatched.
- Session titles are generated by AI from the first message. A deterministic
  shortened form of that message is persisted first and remains the fallback.
- Titles are mutable, non-unique display metadata. Stable `session-N` values
  remain the identity.
- Renaming is available only through the TUI session browser.
- Removal is permanent. After explicit confirmation, it cancels active work,
  terminates jobs, disconnects clients, and deletes durable state.
- Visible transcript state is durable, including failed, cancelled, and
  interrupted turns. Only successful user/assistant exchanges enter model
  context.
- Active jobs and model requests survive switching and client detachment but
  remain process-local. They do not survive backend death or machine restart.

## Architecture and Ownership

### Terminal controller

The terminal composition root passes the connected backend and launch intent
to a new terminal-facing controller rather than opening one fixed session in
`main` and passing only its capability to the application.

The controller owns:

- the typed backend connection;
- the active project working directory;
- either an ephemeral draft or one attached durable session;
- local browser state and refresh timing.

Its current-chat state is one of:

1. `Draft`: an ephemeral working directory, model catalog, selected model,
   selected reasoning level, editor, and local presentation state;
2. `Attached`: one typed session capability plus the authoritative
   `SessionSnapshot` projection.

The draft is not a second backend session model. It has no ID, actor, title,
history, jobs, persistence warning, or observer. The backend supplies the
catalog and defaults used to initialize it. Model and reasoning changes made
in a draft are sent with the first materialization request.

After a global switch, the selected session's persisted working directory
becomes the active project. The local browser view and a later `/new` use that
directory.

### Backend and manager

The backend remains authoritative for durable identity, transcripts, titles,
actors, lifecycle mutation, and listings. The `SessionManager` gains commands
for:

- atomic startup selection and attachment;
- first-message materialization and submission;
- local and global listing with live overlays;
- opening by stable ID or unambiguous title;
- rename;
- deletion;
- exact attachment detachment.

The old default-session designation no longer participates in selection and is
removed from the domain model during migration.

### Session actors

Actors remain the exclusive owners of a materialized session's harness,
projection, settings, jobs, observers, dirty checkpoint, and active run.
Renames and title-generation results pass through the actor when it is live so
snapshot updates remain ordered with other session events. The manager updates
cold sessions directly through the repository.

Deletion is manager-owned because it must coordinate the actor, repository,
and every attachment rather than behave like an ordinary in-session command.

### Title generator

Title generation is an injected backend service separate from conversation
execution. It uses the session's initially selected model at that model's
lowest supported reasoning level, receives only the first user message and a
small title instruction, and cannot read or modify model-visible history.

The title task contributes to backend activity so automatic shutdown does not
interrupt it, but it does not make the session appear to have a running model
request. It uses the completion transport's existing bounded request timeout;
timeout is an ordinary title-generation failure. Tests use a deterministic
fake title generator and never require live network access.

## Empty State and Startup

### Plain startup

Plain `moh` canonicalizes its invocation directory, connects or spawns the
backend, and asks the manager to select the most recently active running
session for that exact directory. Selection and attachment happen in one
manager command so a list/open race cannot choose a stale candidate.

Running candidates are ordered by descending live activity time and then
descending stable ID for a deterministic tie break. If no candidate is
running, the backend returns draft defaults and the client shows an ephemeral
empty chat.

Idle saved sessions are resumed through `/sessions` or an explicit CLI
selector; plain startup does not pick one merely because it exists.

### `/new`

`/new` accepts no arguments. It explicitly detaches the current durable
session, if any, and opens a new draft in the active project without consulting
other running sessions. Extra arguments produce local usage feedback and are
never submitted to the model.

### First submission

A nonblank first prompt is submitted through one backend-level operation. The
manager:

1. validates the prompt, working directory, and draft settings;
2. derives the deterministic fallback title;
3. transactionally creates the session identity, settings, fallback title,
   visible user transcript entry, and running turn record;
4. materializes the actor and attaches the requesting client;
5. dispatches the conversation run;
6. starts independent AI title generation.

Persistence completes before model dispatch. If the storage transaction fails,
no partial session exists and the prompt remains in the client editor. If
dispatch fails after materialization, the actor durably records a failed turn.

The client receives an attachment snapshot and run result using the same
observer sequencing rules as an ordinary open. It cannot miss early run
events between materialization and observer installation.

### Exit

Ctrl+C and `/quit` discard a draft without contacting session persistence.
They explicitly detach an attached session before the backend connection is
closed. Connection teardown remains the fallback that removes all attachments
owned by that connection.

## Titles and Rename

### Deterministic fallback

Moh normalizes the first message by collapsing Unicode whitespace to single
spaces and trimming the result. It shortens the normalized text to at most 64
Unicode scalar values, preferring a word boundary and adding an ellipsis when
truncation leaves room. The first-message validator guarantees a non-empty
source.

This fallback is persisted in the first session transaction. The session
therefore always has a usable title even if title generation never starts,
times out, returns invalid text, or the backend exits.

### AI result

The title prompt asks for one concise plain-text title of roughly three to
eight words. Moh uses the first non-empty returned line, removes control
characters and surrounding quotes or Markdown decoration, collapses
whitespace, and limits the result to 64 Unicode scalar values. Empty or invalid
output is treated as failure and leaves the fallback unchanged.

The session row carries a title revision and title source. Title generation
captures the pending revision and uses compare-and-set semantics. A manual
rename changes the revision and source, so a delayed AI result can never
overwrite it.

AI failure is intentionally silent because the persisted fallback is already
valid. A successful AI result emits an ordered title-changed session event and
appears in later browser refreshes.

### Manual rename

Manual titles must contain 1-64 Unicode scalar values, have no leading or
trailing whitespace, and contain no control characters. Duplicate titles are
allowed. Rename errors preserve the entered value in the inline editor.

CLI title lookup remains scoped to the invocation directory. One exact match
opens the session. Multiple matches return a typed ambiguity result containing
the stable IDs the user can select explicitly.

## Durable Data Model

### Session metadata

The next transactional SQLite schema version stores:

- stable session ID;
- canonical working-directory bytes;
- mutable title, title source, and title revision;
- model, reasoning, and context settings;
- creation and latest activity times.

Titles are indexed for lookup but are not unique. The default marker and
CWD-scoped unique-name constraint are removed.

### Transcript and model history

Durable presentation and model context are separate concerns:

- transcript records preserve the ordered visible projection: submitted user
  messages, terminal assistant answers, visible tool activity, failures,
  cancellations, and interruptions;
- successful history retains only completed user/assistant exchanges used to
  build future model requests;
- durable turn state identifies a submitted prompt as running, completed,
  failed, cancelled, or interrupted.

Assistant deltas are provisional and are not checkpointed individually. A
successful completion transaction writes the final assistant transcript item,
the successful history pair, context metadata, and terminal turn state. Failure
and cancellation transactions write their terminal visible item without
adding model history.

If the backend dies with a durable running turn, the next load atomically marks
it interrupted and adds one idempotent visible interruption item. The run is
not resumed automatically.

### Migration

Migration is transactional and preserves existing successful conversations and
settings:

- existing names become titles;
- unnamed sessions with history receive a deterministic title derived from
  their first user message;
- existing user/assistant history becomes both transcript entries and
  successful model history;
- legacy empty session rows are removed because they represent states that are
  intentionally ephemeral in the new model;
- default markers and unique-name constraints are retired;
- migration does not make AI title requests.

On migration failure the old database is not partially modified. Existing
corruption quarantine and startup-warning behavior remains in force.

## Session Browser

### Opening and modes

`/sessions` opens a Ratatui modal over the current chat or draft. It captures
input while open and always starts in the local mode for the active project.
`Tab` switches between:

- local: durable sessions for the active working directory;
- global: every durable session, grouped by working directory.

The active project's group comes first in global mode. Other groups are
ordered by descending latest session activity, and rows within every group are
ordered by descending activity. Descending stable ID breaks ties.

The browser refreshes once per second only while open. A failed refresh keeps
the last good rows and shows a non-destructive warning. Successful refreshes
preserve the filter and selected stable ID when it still exists.

### Rows and filtering

Rows display the title, stable ID, last activity, current marker, active model
run, running-job count, and attachment count. Global rows also display their
working-directory group. The current chat's title is shown in the normal status
line beside its working directory; a draft displays `new chat`.

Typing in the browser fuzzy-filters title, ID, and lossy working-directory
display text. Filtering never changes the raw bytes used for identity or
grouping.

### Controls

- Up/Down move one row.
- PageUp/PageDown move by one visible page.
- The mouse wheel scrolls the list while the modal is open.
- Enter switches to the selected session.
- `F2` opens the inline rename editor.
- Ctrl+D opens the destructive confirmation dialog.
- Escape closes rename or confirmation first, then the browser.

There is no create action in the browser.

### Switching

Switching opens and validates the target attachment before detaching the old
one. A failed open leaves the old session visible and attached and keeps the
browser open. After a successful open, the controller:

1. installs the target snapshot and observer;
2. explicitly detaches the previous attachment without cancellation;
3. updates the active project to the target working directory;
4. clears session-specific local notices, menus, scroll state, and editor
   state;
5. closes the browser and renders the target.

A detach failure after the new session opens is reported as a warning; backend
connection teardown still guarantees eventual cleanup.

## Rename and Delete Flows

### Rename

The browser sends rename by stable ID. A live actor orders the metadata change
with session events and broadcasts it to every observer. A cold session is
updated through the repository. The initiating browser stays open, retains its
selection, and refreshes the affected row. If it renamed the current session,
the background status line updates as well.

### Confirmation

Deletion confirmation names the title and stable ID and explicitly states that
active model work and background jobs will be cancelled and all attached
clients disconnected. Confirmation is required for idle and running sessions.

### Manager-coordinated deletion

The manager serializes deletion against opens, commands, and concurrent
deletion attempts:

1. mark the session deleting so new commands and attachments are rejected;
2. ask a live actor to cancel its model run, terminate and reap running jobs,
   and durably record the resulting cancellation state;
3. transactionally delete the session row with cascading transcript, turn,
   and history cleanup;
4. broadcast a typed session-deleted terminal event and close attachments;
5. remove the actor from the manager.

If cancellation or persistence fails before the delete transaction, the row is
not deleted and the user is not told removal succeeded. The manager clears the
deleting state and leaves or rematerializes the session in a resumable state;
its active work may already have been cancelled. Other sessions remain
available throughout.

Deleting a non-current browser row keeps the browser open. Deleting the current
session closes the browser and applies startup selection for the deleted
session's project: attach the most recently active running session, or show a
draft. Clients whose current session is deleted remotely apply the same
fallback after receiving the terminal event.

Deletion is permanent. Trash, archive, restore, and undo are outside this
milestone.

## Protocol Changes

The versioned Cap'n Proto protocol adds typed request/result unions for:

- startup selection returning either an attached session or draft defaults;
- materialize-and-submit returning the attachment and assigned run ID;
- listing with local or global scope;
- rename;
- deletion;
- explicit attachment detachment;
- ambiguous title lookup;
- title-changed and session-deleted observer events.

Session summaries add title, running-job count, and a derived running flag.
Default and optional-name fields are retired. CWD remains raw bytes plus a lossy
display string for non-Rust clients.

Every attachment has an ID unique within its backend connection. Actors key
observers by connection and attachment ID. Explicit detach removes only that
attachment; connection teardown removes every remaining attachment owned by
the connection.

The protocol version and advertised feature set advance together. Older
clients receive the existing actionable incompatibility error rather than
silently receiving partial session-management behavior.

## CLI Behavior

Supported forms become:

~~~text
moh
moh --new
moh --session SELECTOR
moh sessions
moh server
~~~

- `moh` applies startup selection for the invocation directory.
- `moh --new` always opens a draft.
- `moh --new NAME` is rejected; manual title changes are TUI-only.
- `moh --session session-N` opens the stable ID globally.
- `moh --session TITLE` opens one exact title match in the invocation directory
  or reports ambiguity with matching IDs.
- `moh sessions` lists durable sessions in the invocation directory and never
  materializes a draft.

The interactive browser, not an additional CLI flag, provides global browsing.

## Error Handling

- Draft materialization failure keeps the prompt and draft settings intact.
- A run-start failure after materialization becomes a durable failed turn.
- Switch failure preserves the old attachment and browser selection.
- Rename failure preserves the inline editor and submitted title.
- Delete failure preserves the session and never reports success.
- Browser refresh failure preserves the last good listing.
- AI title failure retains the deterministic fallback without an intrusive
  transcript error.
- A deleted-session event triggers startup fallback rather than a generic
  observer-closed failure.
- Sequence-gap recovery remains snapshot-based; a missing deleted session is
  converted into the same typed deleted-session transition.
- Dirty checkpoint warnings remain session-scoped. Automatic shutdown retries
  them and refuses to exit while committed state cannot be saved.
- Backend connection failure still restores the terminal before reporting the
  sanitized error.

## Testing Strategy

Implementation follows test-driven development. Tests use fake engines, title
generators, clocks, and repositories where required.

### Store and migration

- drafts create no files or rows;
- first submission creates session, fallback title, visible prompt, and running
  turn atomically;
- successful, failed, cancelled, and interrupted transcript restoration;
- successful-only model history reconstruction;
- idempotent interruption recovery;
- duplicate titles and ambiguous lookup;
- title revision compare-and-set and manual-rename race;
- local and global ordering;
- cascading deletion and rollback behavior;
- transactional migration of named, unnamed, and empty legacy sessions.

### Manager and actor

- most-recent running startup selection, including run and job activity;
- deterministic tie breaking and empty fallback;
- `/new` semantics independent of running sessions;
- materialize-before-dispatch ordering;
- title generation success, invalid output, failure fallback, and manual-win
  race;
- open-target-before-detach switching;
- exact attachment accounting across repeated switches;
- multi-client rename propagation;
- deletion of idle, running, job-owning, current, and remotely attached
  sessions;
- deletion failure recovery and cross-session isolation;
- shutdown waits for title generation and dirty checkpoints.

### RPC and transport

- schema conversion round trips for every new value and result union;
- Unix RPC startup, materialization, local/global listing, switch, rename,
  delete, explicit detach, ambiguity, and terminal observer events;
- protocol feature negotiation and incompatible-client reporting;
- callback ordering during first submission and remote deletion;
- connection teardown removes attachments left after an explicit-detach
  failure.

### Client and Ratatui

- plain startup, `/new`, `/sessions`, and draft settings;
- first-prompt preservation on materialization error;
- local/global mode reset and switching;
- grouping, sorting, fuzzy filtering, selection preservation, and refresh
  failure;
- keyboard and mouse-wheel browser controls;
- inline rename and nested deletion confirmation;
- switching while the old session runs and rendering its later snapshot;
- current and remote deletion fallback;
- authoritative title/status updates;
- visible cell and style assertions for modal layout, selected row, current and
  running markers, group headings, nested dialogs, and empty states;
- terminal cleanup on every new exit and failure path.

### Acceptance and verification

A real PTY check covers:

- alternate-screen restoration after browsing and switching;
- switching away from active model work and observing its updated transcript on
  return;
- switching away from a running background job;
- deleting active work after confirmation;
- local/global modes, filtering, wheel scrolling, and resize/reflow;
- empty drafts remaining absent from the browser and database.

The final automated gate is:

~~~text
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-targets
cargo build --locked
git diff --check
~~~

Live title generation is qualified separately with the configured Codex
account and is not required by deterministic automated tests.

## Acceptance Criteria

The milestone is complete when:

- plain `moh` resumes the most recently active running local session or shows a
  non-durable empty chat;
- `/new` always opens a non-durable empty chat and accepts no arguments;
- first submission durably materializes the session before model execution;
- AI title success is persisted, failure retains the deterministic fallback,
  and manual rename wins every race;
- `/sessions` browses local and global saved sessions in a modal without a
  create action;
- switching detaches without cancelling and the previous session continues its
  run or jobs in the backend;
- visible successful, failed, cancelled, and interrupted transcript state
  survives backend restart while model context contains only successful
  exchanges;
- titles can duplicate, rename is TUI-only, and ambiguous CLI lookup reports
  stable IDs;
- confirmed deletion cancels active work, reaps jobs, disconnects clients, and
  permanently removes durable state;
- deleting the current or remotely attached session applies deterministic
  startup fallback;
- empty drafts never appear in local/global listings or durable storage;
- all automated verification and PTY acceptance checks pass.
